# Отчёт по коду Blaze

Дата подготовки: **1 октября 2026 года**. Версия: **0.1.0**. Основание: чтение текущих исходников, проверка синтаксиса и поведенческие проверки таймера и аналитики. Это технический обзор прототипа, а не независимый аудит безопасности или подтверждение готовности к выпуску.

## 1. Текущая архитектура

Интерфейс построен на HTML, CSS и обычном JavaScript. Electron 42.11.8 создаёт основное окно, отдельные окна виджетов и трей. На Windows дочерний процесс PowerShell опрашивает активную программу.

| Слой | Файлы | Ответственность |
| --- | --- | --- |
| Основной интерфейс | `index.html`, `app.js` | Навигация, заметки, карта, библиотека, календарь, настройки |
| Оформление | `styles.css`, `design.css` | Базовая сетка, компоненты и адаптация макетов |
| Виджеты | `widget.html`, `widget.js`, `widget.css` | Отдельные представления, задачи, кнопки таймера и закрепления |
| Аналитика | `analytics.js` | Ключи периодов, суммы по дням/месяцам, время приложений |
| Цвета | `color-utils.js` | Проверка HEX и выбор контрастного текста |
| Процесс Electron | `desktop/main.cjs` | Окна, IPC, уведомления, трей, сохранение статистики |
| Мост | `desktop/preload.cjs` | Ограниченный API между интерфейсом и Electron |
| Учёт Windows | `desktop/tracker.ps1` | Название активного процесса и время без ввода |
| Таймер | `desktop/focus-timer.cjs` | Единое состояние фокуса и завершение сессии |
| Диагностика | `desktop/runtime-logging.cjs` | Локальный журнал и обработка закрытых каналов вывода |
| Предпросмотр | `server.cjs`, `design-preview.js`, `widget-preview.js` | Браузерный режим и изолированные демонстрационные данные |

Основное окно сохраняет состояние и отправляет обновления открытым виджетам. Виджет может изменить пункт задачи или состояние закрепления; процесс Electron передаёт изменение обратно основному окну. Таймер находится в процессе Electron, поэтому несколько окон фокуса отображают одно состояние.

## 2. Хранение данных

- `localStorage`, ключ `blaze-state`: виджеты, заметки, собственные цвета, отметки рабочих дней, часы, комментарии, цель и адреса маршрута.
- `%APPDATA%\blaze-workspace\activity.json`: накопленное время по датам и названиям процессов.
- `%APPDATA%\blaze-workspace\activity-sessions.json`: история программ и фокуса.
- `%APPDATA%\blaze-workspace\runtime-errors.log`: диагностика запуска и ошибок.

Файлы статистики сохраняются через временный файл и переименование. У основной модели есть номер версии, но полноценной системы миграций и валидации всех вложенных полей пока нет. Данные не шифруются приложением. Отдельные JSON-файлы и localStorage не образуют общую транзакцию.

Экспорт состояния доступен в интерфейсе, но его не следует считать полной резервной копией всей нативной статистики. Позиции окон сейчас не сохраняются; при повторном открытии окна раскладываются с заданным смещением.

## 3. Реализованные сценарии

**Заметки.** Заголовок, свободный текст и список задач; изменённые отметки передаются из отдельного окна в основное. Текст экранируется перед вставкой в HTML. Пользователь выбирает размер и цвет, включая собственный HEX.

**Маршрут.** Blaze формирует URL официального встроенного виджета Яндекс Карт, передаёт два адреса и режим движения. Расчёт времени, остановки и варианты пути находятся внутри карты. Blaze не получает эти данные обратно из стороннего iframe. Компактная схема в карточке остаётся иллюстрацией.

**Учёт программ.** Опрос раз в пять секунд. После 60 секунд без ввода очередной интервал не учитывается. Сохраняется имя процесса, а не заголовок окна, содержимое документа или нажатия клавиш. Это приблизительное измерение: переходы между приложениями внутри интервала и задержки процесса могут влиять на точность.

**Рабочие дни.** Ручная отметка дня, число часов, комментарий и месячная цель. Старые отметки без часов не должны восприниматься как автоматически восстановленные часы работы.

**Фокус.** Пауза, продолжение, добавление пяти минут и завершение. Подсчёт опирается на время окончания, а не только на количество тиков. После полного выхода из приложения активный таймер не восстанавливается. Время фокуса и активность программ — разные показатели: их нельзя складывать без устранения пересечений.

**Отдельные окна.** Каждое окно можно перемещать за заголовок. Закрепление включает `alwaysOnTop`; перемещение остаётся разрешённым. Закрытие виджета убирает его с экрана, а не удаляет его содержимое.

## 4. Границы доступа

В окнах включены `contextIsolation` и `sandbox`; `nodeIntegration` выключен. Preload предоставляет конкретные операции, а не произвольное выполнение команд. Обработчики основных операций проверяют отправителя IPC. Для виджета ограничены тип, длина текста, режим маршрута, размер и цвет.

Основные всплывающие окна и переходы обрабатываются через фильтрацию адресов Яндекса. Запросы разрешений web-содержимого отклоняются. Проверка не подтверждает полную изоляцию сторонних iframe: загрузка карты остаётся внешним сетевым взаимодействием.

Перед публичным выпуском стоит добавить явную Content Security Policy, отдельно проверить ограничения навигации/iframe и валидировать схему статистики и восстановленного состояния. Разрешения и ограничения браузерного предпросмотра отличаются от нативного приложения.

## 5. Качество и проверки

`pnpm check` проверяет синтаксис основных JavaScript-файлов и запускает `verify-behavior.cjs`.

Поведенческие проверки покрывают:

- сохранение оставшегося времени на паузе;
- продолжение сессии и добавление времени;
- завершение и подсчёт отработанных секунд;
- добавление времени до старта;
- двенадцать уникальных месяцев на границах года, включая 31-е число и високосный февраль;
- суммы времени приложений за период.

В прошлой визуальной проверке просматривались главная, активность, рабочие дни и галерея самостоятельных виджетов. Проверки не заменяют полный сценарий на разных версиях Windows, мониторах и масштабах экрана. Маршруты зависят от доступности Яндекс Карт и не проверяются модульным тестом.

## 6. Известные ограничения и технический долг

| Приоритет | Наблюдение | Следующий шаг |
| --- | --- | --- |
| Высокий | Нет полноценного установщика и готового релизного процесса | Сборка Windows-пакета, тест чистой установки, подпись и политика обновлений |
| Высокий | Нет восстановления позиций окон и активного таймера | Сохранять координаты с проверкой доступных мониторов; определить поведение после выхода |
| Высокий | Модель сохранённых данных валидируется частично | Схема данных, миграции, обработка повреждённых файлов |
| Средний | Основная логика сосредоточена в `app.js`, часть стилей переопределяется в `design.css` | Разделить доменную логику, рендеринг и обработчики; собрать единые токены |
| Средний | В годовой аналитике среднее делится на 365 независимо от выбранного года | Определить период расчёта и учитывать число дней, в том числе високосный год |
| Средний | «Месяц» аналитики использует окно дней, заканчивающееся выбранной датой | Уточнить UX: календарный месяц или скользящий период |
| Средний | Имена приложений основаны на ProcessName, без нормализации и реальных иконок | Словарь имён, политика группировки, безопасное получение иконок |
| Средний | История сессий ограничивается при добавлении программ, но не единым способом для всех типов | Общий лимит и правила хранения/удаления истории |
| Средний | Запись статистики и обновление интерфейса происходят периодически | Описать возможную потерю последних секунд при аварии; добавить проверки восстановления |
| Средний | Учёт рабочего времени зависит от системного времени и опроса | Проверить сон/пробуждение, смену даты, часового пояса и ручную коррекцию часов |
| Средний | Нет полного E2E-набора | Проверить создание, цвет, закрепление, перемещение, задачи, календарь и выход |
| Низкий | Демонстрационный режим живёт рядом с рабочим интерфейсом | Выделить отдельную сборку предпросмотра перед релизом |

## 7. Рекомендованный порядок развития

Сначала стабилизировать данные и окна, затем подготовить установку и восстановление после ошибок. После этого провести сценарную проверку доступности и дизайна. Облачную синхронизацию, мобильные клиенты и плагины лучше рассматривать после стабилизации основной модели.

Закрытый репозиторий фиксирует исходную точку разработки. Отчёт описывает состояние на указанную дату; обновлять его следует вместе с изменениями продукта.
